## 2. Перенос файлов на Яндекс.Диск

Два варианта, нужно выбрать один:

**А. Монтирование Диска как сетевой папки (rclone mount / webdav), код почти не трогаем.**
`rclone` уже есть в зависимостях бэкапа. Поднимаем `rclone mount yadisk: /data/disk --vfs-cache-mode writes` в контейнере `backend` (или отдельным sidecar-контейнером), и постепенно переключаем пути `uploads`/`docs`/`thumbs`/`public`/`site` с локального volume на этот путь.
Плюсы: минимум правок в `images`, `siteimg`, `notebook`, `plans`. Минусы: FUSE в Docker требует `--cap-add SYS_ADMIN` или `--device /dev/fuse`, задержка на каждый файл чуть выше локального диска.

**Б. Прямая работа с Яндекс.Диск REST API в коде (без FUSE).**
Отдельный `YandexDiskService` (`PUT /v1/disk/resources/upload`, `GET /v1/disk/resources/download`, `GET /v1/disk/resources`) с токеном из `.env`. Код в `images`/`siteimg`/`notebook` переходит с `fs.writeFile`/`fs.readFile` на вызовы этого сервиса.
Плюсы: честная облачная интеграция, не завязана на FUSE в контейнере. Минусы: больше кода, нужен кэш превью (`thumbs`) локально, иначе каждая миниатюра — отдельный HTTP-запрос на Диск.

**Рекомендация:** начать с **А** (rclone mount) — он уже частично в проекте (используется для офсайт-бэкапа), даёт результат быстрее и без переписывания модулей `images`/`siteimg`/`notebook`. К **Б** переходить только если производительности rclone mount не хватит.

**Получение токена Яндекс.Диска (ручная разовая настройка, Redirect URI `verification_code` — это «токен для приложения», без своего веб-сервера):**
1. Открыть `https://oauth.yandex.ru/authorize?response_type=code&client_id=984daaf7cc224164aa22d92f03d7da4e` в браузере владельца, разрешить доступ.
2. Яндекс покажет код на странице `oauth.yandex.ru/verification_code` — скопировать.
3. Обменять код на токен: `curl -X POST https://oauth.yandex.ru/token -d grant_type=authorization_code -d code=<код> -d client_id=<ClientID> -d client_secret=<secret>`.
4. Полученный `access_token` положить в `.env` как `YANDEX_DISK_TOKEN` (не в git, не в чат). Токен долгоживущий, но может быть отозван владельцем в настройках Яндекс ID — тогда шаги 1–3 повторить.
5. Для `rclone`: `rclone config` → тип `yandex` → вставить тот же токен (rclone умеет сохранять токен в `rclone.conf`, который тоже не кладём в git).

**Миграция существующих файлов:** одноразовый `rclone copy backend/data/uploads yadisk:korean/uploads` (и так же `thumbs`, `docs`, `public`, `site`) после настройки remote, до переключения кода на новый путь.

## 5. Доступы из демо-приложения Яндекс

- `ClientID` и `Client secret` — это OAuth-приложение «Диск REST API», используется только для пункта 2 (получение `YANDEX_DISK_TOKEN`). Secret в этот файл не вписан — положить прямо в `.env` под именем `YANDEX_DISK_CLIENT_SECRET`, `ClientID` — `YANDEX_DISK_CLIENT_ID`.
- `nik.lyamkin@yandex.ru` — почта оповещений самого OAuth-приложения в консоли Яндекса (куда Яндекс пишет про само приложение), с функциями сайта не связана, менять/использовать в коде не нужно.
- Запрошенные права (доступ к папке приложения / чтение всего Диска / запись в любом месте / информация о Диске) — этого достаточно и для варианта А (rclone), и для варианта Б (REST API).

## Порядок внедрения (по одному пункту, как договорились по работе с правками)

1. Получить `YANDEX_DISK_TOKEN` (ручные шаги выше), проверить `rclone lsd yadisk:` вручную.
2. Настроить `OFFSITE_RCLONE` для ночной копии (пункт 3, самое безопасное — ничего не ломает, копия просто появляется ещё и на Диске).
3. Перевести полный архив с почты на Диск, убрать/сократить `BACKUP_MAIL_TO` (пункт 3).
4. Telegram-канал для кода входа + переключатель в кабинете (пункт 1) — не зависит от пунктов 2 и дальше, можно делать параллельно.
5. Перенос `uploads`/`thumbs`/`docs`/`public`/`site` на Диск (пункт 2) — самый рискованный шаг (трогает каждую страницу с картинками), делать последним и на демо-данных сначала.
6. Обновить `docs/backup.md`, `docs/server.md`, `.env.example`.
