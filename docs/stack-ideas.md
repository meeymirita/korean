# Модный стек: что реально стоит брать (заметка, не план)

Повод: список технологий (Postgres, Redis, Meilisearch, BullMQ/RabbitMQ, Docker, GitHub Actions, Prometheus+Grafana,
Loki+OpenTelemetry, Kubernetes+Helm, Terraform+Ansible, Prisma, MinIO, Sentry, k6, Playwright...) — проверено, что из
этого даёт реальную пользу для **личного** проекта на одном VPS с одним-двумя пользователями, а что не нужно и только
добавит работы. Это не подтверждённый план, а честная сверка «хочу → надо ли».

Текущее состояние (на 2026-11-05): Nuxt SSR + NestJS + SQLite (`node:sqlite`), один VPS, Caddy + systemd,
`scripts/deploy.sh`, CI и автодеплой через GitHub Actions уже есть (`.github/workflows/ci.yml`, `deploy.yml`).
В кабинете уже есть своя аналитика: `AnalyticsPanel.vue`, `ReportTab.vue`, `ReportChartModal.vue`, `LineChart.vue`
(данные из `backend/src/progress/progress.service.ts`).

## Стоит сделать (польза больше работы)

- **Docker + Docker Compose.** Один `docker-compose.yml` вместо ручного Caddy+systemd, воспроизводимое дев-окружение.
  Небольшой разовый труд, понятная выгода.
- **GitHub Actions + автодеплой.** Уже есть, ничего добавлять не нужно.
- **Prometheus + Grafana (только эти два, без Loki/OTel/Sentry) — для операционных метрик, не для пользовательской
  статистики.** Запросы/сек, время ответа и ошибки NestJS, успешность ночных бэкапов (`backup.sh`,
  `install-backup-timer.sh`), память/CPU/диск VPS, аптайм. Пара контейнеров + `node_exporter` + лёгкий
  `/metrics`-эндпоинт в Nest. Разумный объём работы, реальная польза (видно, что сервер жив и бэкапы прошли).
  **Важно:** учебную статистику (ответы/время/темы/прогноз повторений) в Grafana переносить не нужно — она уже
  красиво сделана под пользователя в кабинете (`AnalyticsPanel`, `ReportChartModal`), Grafana для такого не
  предназначена (это ops-панели, а не «сторителлинг» для ученика) и получится хуже, чем то, что уже есть.

## Можно, но не обязательно (нейтрально)

- **PostgreSQL вместо SQLite.** Реальная миграция (`backend/src/db/db.service.ts`, возможно Prisma/TypeORM).
  На нынешних объёмах SQLite не бутылочное горлышко — смысл только учебный.
- **Redis + BullMQ.** Если возьмёшь Postgres — Redis для кэша/сессий недорог. BullMQ может заменить cron-скрипты
  (дайджесты, ночные копии) на управляемые задачи с ретраями — разумно, но не обязательно, cron и так работает.
- **Meilisearch.** Только если реально не хватает поиска по словам/грамматике сейчас. Решение без текущей проблемы.

## Не стоит (оверхед без пользы на этом масштабе)

- **RabbitMQ вместе с BullMQ.** Два инструмента под одну задачу — избыточно. Если берёшь очередь, это BullMQ
  (поверх Redis), Rabbit не нужен вообще.
- **Kafka.** Это распределённый лог событий для высокого потока и множества независимых consumer'ов — не очередь
  задач. Нужен кластер (ZooKeeper/KRaft + брокер), партиции, retention, consumer groups. У нас пара джобов в сутки
  (бэкап, дайджест, напоминания) на одном процессе — Kafka тут даже более неуместна, чем RabbitMQ. Если очередь
  когда-то понадобится — BullMQ поверх Redis, этого достаточно.
- **Kubernetes + Helm.** Один VPS, одно приложение без нагрузки, требующей масштабирования. K8s — это кластер,
  networking, ingress, secrets, постоянная операционная нагрузка на одного человека ради нулевой практической
  выгоды. Задеплоить технически можно (хоть k3s на том же VPS) — но не ради прод-пользы, только как отдельная
  учебная песочница.
- **Terraform + Ansible.** Имеет смысл при нескольких окружениях/серверах. Один VPS и `deploy.sh` уже решают задачу
  без ритуала IaC.
- **Loki + OpenTelemetry + Sentry.** Полноценный трейсинг нужен распределённым системам; тут монолит на одном
  сервере. Sentry без потока реальных ошибок от живого трафика будет просто пустовать.
- **MinIO.** Файлов (картинки заметок, аватары) немного, локальный диск на VPS справляется; S3-совместимое
  хранилище имеет смысл при большом объёме медиа или нескольких серверах — не здесь.

## Итог

Полный список внедрять нецелесообразно — классический резюме-стек для проекта, где он не нужен. Минимально разумный
набор: Docker Compose, по желанию Postgres + Redis/BullMQ, и отдельно — Prometheus + Grafana именно для
операционных метрик сервера (не для учебной статистики, она уже есть и сделана лучше, чем сделает Grafana).
Остальное — K8s, Terraform/Ansible, Rabbit, Loki/OTel/Sentry, MinIO — либо чисто учебная песочница в стороне,
либо не трогать.
